# Бесплатное размещение: Vercel + Render + Turso

## Текущее состояние
Frontend уже отвечает на https://ai-code-mentor-frontend-iota.vercel.app . Проверено наличие учебного интерфейса и runner.js. Backend на https://ai-code-mentor-backend-z80q.onrender.com после прогрева вернул OpenAPI с /learning/groups. Это подтверждает существующее размещение, но не сохранность локальной базы при рестарте.

Официальные условия проверены по ссылкам ниже. Render Free засыпает после 15 минут без входящих запросов; первое открытие может быть медленным. Локальные файлы, включая SQLite, теряются при перезапуске/сне/новом deploy. Бесплатный Render Postgres истекает через 30 дней, поэтому он не выбран как постоянное решение. Turso предоставляет бесплатный план в пределах квот; код выбирает официальный SDK по исходному URL: **turso:// → turso_serverless**, **libsql:// → libsql**. Префикс адреса нельзя заменять наугад.

## Что изменено в коде
- Локальный запуск по-прежнему использует sqlite3 и DATABASE_PATH.
- При TURSO_DATABASE_URL все рабочие соединения направляются непосредственно в облачную базу Turso/libSQL, а не в временную копию файла на Render. Токен передаётся отдельно от URL.
- Удалённый режим не переключается молча на локальную базу при отсутствии токена или ошибке запроса.
- REQUIRE_REMOTE_DATABASE=true запрещает запуск с временным SQLite-файлом при забытом URL.
- Сохранены именованные строки, параметры SQL, транзакции, проверки доступа и обработка ограничений целостности.
- При удалённой базе не выполняется VACUUM. Health-проверка возвращает HTTP 503 при неработающей базе, а в checks.database.backend показывает turso либо sqlite, без адреса и секретов.

## Перед переключением существующего сервиса
Сначала выяснить, есть ли важные данные на текущем Render. Само включение Turso **не переносит старые записи**. Не делать redeploy, если нужно сохранить текущие аккаунты и работы, пока не получена проверенная копия и не определён перенос. У бесплатного Render ограничен доступ к файловой системе; универсальная команда выгрузки через SSH не предполагается. Старый scripts/migrate_to_postgres.py для этого не подходит: это другой движок и скрипт удаляет таблицы назначения.

Если есть только тестовые данные и допустима новая пустая база, можно перейти к настройке ниже. Не загружать на внешний сервис tracked code_mentor.db без проверки происхождения и согласованного переноса.

## Настройка в аккаунтах владельца
1. Открыть Turso, войти в свой аккаунт и выбрать бесплатный план. Использовать существующую базу нужного движка; текущий адрес владельца имеет turso://, поэтому используется turso_serverless.
2. Скопировать Database URL вида `turso://…turso.io` либо `libsql://…turso.io` и создать database auth token. URL можно передать для проверки; токен сохранять только в защищённых настройках Render. Пароль, management token и API-ключи не отправлять в чат и не коммитить.
3. Открыть существующий Render-сервис ai-code-mentor-backend → Environment. Сохранить существующие GOOGLE_API_KEY и JWT_SECRET. Не менять JWT_SECRET при каждом запуске: это инвалидирует вход пользователей.
4. После публикации совместимого кода внести одновременно:

| Переменная | Значение |
| --- | --- |
| TURSO_DATABASE_URL | Исходный Database URL своей базы без замены префикса |
| TURSO_AUTH_TOKEN | Секретный database auth token — только в Render |
| REQUIRE_REMOTE_DATABASE | true |
| REQUIRE_EMAIL_VERIFICATION | false для текущего демо-сценария без SMTP |
| FRONTEND_ORIGINS | https://ai-code-mentor-frontend-iota.vercel.app |

Существующий CORS также допускает два известных домена frontend; дополнительные домены задаются FRONTEND_ORIGINS. Удалённый токен не следует добавлять в frontend, Vercel, HTML или публичный GitHub.

5. Build command: `pip install -r requirements.txt`. Start command: `uvicorn main:app --host 0.0.0.0 --port $PORT`. Runtime — Python, plan — Free, health check — /health. Для бесплатного варианта не создавать платный диск или платную Render Postgres-базу.
6. Сохранить Environment и выполнить deploy обновлённого backend после согласования судьбы старых данных. На существующем Render сервисе для этого нужны действия владельца либо отдельно авторизованный management API; доступ к аккаунту не предполагается из одного URL.

## Проверка после настройки
- GET /health: HTTP 200, status=healthy и checks.database.backend=turso. Значение sqlite означает, что облачная база ещё не активирована.
- GET /openapi.json: есть /learning/groups.
- Создать временный аккаунт, войти, создать группу и задание, пройти учебный сценарий.
- Перезапустить backend и подтвердить, что тот же аккаунт и задание сохранились. Затем удалить только созданные для проверки аккаунты.
- Проверить реальный /analyze: секрет Gemini в Render отдельный от секрета в среде разработки. Ключ из среды разработки автоматически в Render не переносится.
- Открыть frontend и проверить регистрацию, тесты, мини-защиту и портфолио.

## Что проверено до получения облачных реквизитов
Официальные libsql 0.1.11 и turso_serverless 0.1.0 установлены с PyPI. Пройдены 52 теста: SQLite, настоящий libSQL-драйвер и локальный движок нового Turso (pyturso 0.8.3). Проверены учебные/API-сценарии, commit/rollback, повторное открытие, ограничения целостности и выбор SDK для turso://. Облачные авторизация, сеть и сохранение после рестарта Render требуют настоящих реквизитов и отдельной проверки — локальные тесты их не подтверждают.

## Сохранённый исходный снимок
В рабочей среде отдельно сохранена исходная SQLite-копия из репозитория, проверена её целостность и записан SHA256. Это **не подтверждённая актуальная копия Render**: данные, появившиеся после её создания, в ней могут отсутствовать. Копия находится вне Git checkout с правами 0600 и не публикуется.

Без актуальной копии текущей Render-базы либо проверенного доступа для выгрузки переключение и redeploy не выполняются. На Free Render доступ к Shell ограничен; если владелец не может получить выгрузку, требуется выяснить у провайдера возможный способ экспорта. Наличие такой возможности или восстановление утраченных данных не гарантируется. Поддержка Turso подготовлена в отдельной ветке; работающая main не изменена.

Для полного локального набора тестов установить requirements-dev.txt. Без необязательного pyturso тесты локального нового движка пропускаются и не должны описываться как пройденные. Локально с pyturso выполнены все 52 теста без пропусков.

## Перенос выбранного SQLite-снимка
Владелец подтвердил, что исходного снимка достаточно. Для выполнения нужны TURSO_DATABASE_URL и TURSO_AUTH_TOKEN в защищённом окружении. Префикс turso:// сохраняется: он выбирает официальный turso_serverless. При работе через прокси секрет должен быть разрешён для реального HTTPS-хоста базы. Для сохранения того же токена через API Render нужно отдельно разрешить api.render.com в привязке секрета; иначе токен вводится владельцем напрямую в Environment Render после переноса, без отправки в чат.

Пример команд, с явным путём к проверенной копии и SHA256 из её локального манифеста:

```bash
python scripts/migrate_snapshot_to_turso.py --source /path/to/backup.sqlite3 --expected-sha256 HASH_FROM_MANIFEST
python scripts/migrate_snapshot_to_turso.py --source /path/to/backup.sqlite3 --expected-sha256 HASH_FROM_MANIFEST --apply --report /private/path/new-migration-report.json
python scripts/migrate_snapshot_to_turso.py --source /path/to/backup.sqlite3 --expected-sha256 HASH_FROM_MANIFEST --verify
```

Без --apply/--verify выполняется только проверка локальной копии. Импорт не перезаписывает непустую базу с отличающимися данными. Повторный запуск при точном совпадении всех исходных полей выполняет проверку без повторных вставок. Переносятся столбцы по именам, включая хеши паролей и идентификаторы; сравниваются количества и полное содержимое через хеширование строк, без вывода пользовательских данных. Новые поля схемы получают штатные значения по умолчанию. При ошибке вставки транзакция откатывается. После commit выполняется сравнение через новое соединение.

Скрипт дополнительно сообщает legacy_unowned_todos: старые задачи без user_id сохраняются, но остаются скрытыми до явного назначения владельцев. Он не приписывает такие задачи произвольному пользователю.

Проверки переноса: тесты SQLite и настоящего локального движка Turso, отказ от перезаписи, повторный запуск, откат, неверный SHA256 и обнаружение изменённых полей. Общий набор — 66 тестов без пропусков при установленных requirements-dev.txt. Реальный выбранный снимок также восстановлен и сверен локально во временной Turso-базе. Облачный перенос и переключение Render остаются отдельными шагами и требуют рабочих секретов.

Порядок переключения: подтверждённый перенос → проверка через новое соединение → проверка текущего сервиса Render и тарифа → настройка его Environment без замены GOOGLE_API_KEY/JWT_SECRET → deploy совместимого коммита → /health с backend=turso → проверка сохранения после рестарта. До успешного переноса обновлять рабочую main не следует.
